# Explicit group-member Phonebook import

In the existing Inbox Group Info panel, members with Phonebook management access see **Save members to Phonebook**. Fetching members refreshes the QR membership list and displays available phone identities, skipped/unavailable identities and remaining contact capacity. Users can search/select members and choose an existing owner phonebook or create a named one. Saving is an explicit action; normal group traffic continues to bypass automatic Phonebook and lead capture.

The shared `/api/workspace/inbox/groups/member-import` GET/POST handlers retain the existing Inbox conversation/QR sharing scope and request-Origin guard. They refresh session, group access and Phonebook read/manage permissions before work and after provider refresh. Offline/stale member metadata is rejected. The POST resolves selected phone numbers against fresh provider membership; client-supplied names/contact fields are never trusted. LID-only/hidden identities are skipped rather than interpreted as telephone numbers.

Imports use the existing owner `phonebook` and `contact` tables. Existing target-book numbers are normalized and skipped; their names/custom fields are preserved. A number in another phonebook can be copied to the chosen target. Owner-row locking serializes this importer with itself and the existing rule-based writer, and target-book ownership is checked under lock. Contact limits and plan expiry are checked in the same transaction as book creation/contact inserts; the whole transaction rolls back if capacity is insufficient. No campaign, bot, lead, consent or outbound-message operation is started by import. Historical legacy CSV/manual writers have their own existing concurrency behavior and are not refactored in this increment.

No schema migration is required. Repeating an existing-book import skips already saved members. A repeated new-book name is rejected and the user can choose that existing phonebook. Membership is capped at the existing 5,000-member metadata snapshot bound. UI strings support English and Arabic, and the preview list renders 100 rows at a time with a separate selection set.

Verification uses unit tests and a disposable MariaDB schema for concurrent duplicate prevention, atomic quota rollback, new-book import and foreign-book rejection. Production acceptance must preview real group data without saving customer contacts unless the operator explicitly chooses a target and presses Import.
