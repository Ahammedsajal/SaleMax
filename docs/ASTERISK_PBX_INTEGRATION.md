# SaleMaX Asterisk and GSM Gateway Integration

Status: local integration slice implemented; no Asterisk or gateway settings have been changed. A read-only production check on 5 October 2026 confirmed the current SaleMaX release does not contain these telephony assets; nothing from this integration is deployed.

## Product scope

Integrate telephony into the existing SaleMaX application. The existing `/admin` platform area owns the global PBX connection, provisioning policy, gateway/route health, and audited setup access. The existing business admin area owns tenant call queues, extension-to-member assignment, schedules, and permitted inbound/outbound policies. Business users receive a **Call Center** item in the existing `/user` sidebar, controlled by the same category, plan, membership, and assigned-navigation checks as other modules. Keep `/admin`, `/admin/login`, `/user`, `/user/login`, and agent entry points intact; do not add another login or application shell.

The selected device is the **four-channel/four-SIM Dinstar UC2000-VE**. Its official datasheet describes both 4- and 8-channel variants, SIP v2/RFC 3261, UDP/TCP/TLS signaling, RTP/SRTP media, optional OpenVPN, VoLTE options, and multiple regional LTE band variants. It lists G.729AB, PCMU, PCMA and G.723.1 codecs; use PCMA/PCMU as the initial Dinstar trunk codec pair and handle browser Opus negotiation separately in Asterisk. The exact regional SKU, firmware, and bands must match the carrier SIMs before purchase or activation. Dinstar's manual describes configuring an IP trunk with the remote SIP server address and port. The intended voice path is four Dinstar channels over a direct-internet, source-restricted PJSIP trunk using TLS signaling and SRTP media, with Asterisk handling extensions, inbound destinations, outbound policy and queues. Configure SIM/channel routing on the Dinstar web UI unless Dinstar confirms a supported voice provisioning API; the listed HTTP API is for SMS. [Dinstar UC2000-VE specifications](https://www.dinstar.com/GSM-3G-LTE-voip-gateway/4-8-ports/) [Dinstar datasheet](https://www.dinstar.com/WEB/files/15277/2018-09-06/UC2000-VE%20GSM%26LTE%20VoIP%20Gateway%20Datasheet.pdf) [Dinstar UC2000-VE/VF/VG user manual](https://www.dinstar.com/WEB/files/15278/2018-09-06/UC2000-VE%26VF%26VG_GSM%20_LTE_VoIP_Gateway_User_Manual.pdf).

Asterisk owns SIP authentication, dialplan, queueing, call recording policy, and provider integration. SaleMaX stores the global ARI endpoint/username and encrypted password from the existing platform-admin panel, and can test both the Asterisk ARI `asterisk/info` response and configured `PJSIP/salemax_dinstar_uc2000ve` endpoint state server-side. The ARI account needs permission to read endpoint status as well as system info. Super Admin setup records the Dinstar fixed public source IP and TLS port, manages inbound/outbound policy for each of the four physical channels, and previews the gateway peer and tenant DID routes; these previews do not configure Asterisk or the gateway. Outbound selectors `9901`–`9904` map to physical `Port-0`–`Port-3`, with four selector digits stripped by the Dinstar route. The SaleMaX API selects the tenant-authorized SIM before originating a call. Each assigned extension now has separate mobile and browser SIP passwords derived from the platform key with tenant/member/endpoint separation. The privileged Asterisk preview contains those passwords and is audited; individual `/api/user/call-center/sip-config` and `/webrtc-config` APIs return only the caller's own endpoint credentials and audit access. The Call Center uses TLS/SRTP mobile details and a local SIP.js 0.21.2 bundle for browser WSS/WebRTC registration and audio; setup requires `SALEMAX_ASTERISK_MOBILE_SIP_HOST`, `SALEMAX_ASTERISK_WS_URL`, and the explicit host allowlist. Asterisk WebRTC still requires its HTTPS/WSS listener or Nginx proxy path, trusted certificate, ICE/media reachability, and a manually applied endpoint config. No browser or mobile credential is an ARI credential. [Asterisk WebRTC setup](https://docs.asterisk.org/Configuration/WebRTC/Configuring-Asterisk-for-WebRTC-Clients/). The Asterisk and gateway configs must be applied and tested before calling is reported ready.

**A live ARI HTTP check is not call-control readiness.** The opt-in event worker feeds tenant-bound inbound and outbound call control locally. Inbound Stasis events validate enabled channel/tenant/queue mappings, reserve a unique SIM lease, answer the gateway leg, ring active queue members on mobile and browser endpoints, and apply first-answer-wins. Outbound requests verify the caller's active extension, tenant entitlement, PBX/gateway state, and an enabled tenant-assigned free SIM; the requested endpoint rings first and the Dinstar cellular leg starts after the agent answers. The called number travels through the authorized ARI event and is not persisted. Ended calls release their SIM lease. `GET /api/user/call-center/calls` provides tenant- or membership-scoped call state without phone numbers or raw Asterisk channel IDs. The bilingual Call Center includes a mobile SIP settings reveal, browser SIP.js registration/audio controls, and an outbound call form; browser calls can be selected only after browser SIP registration. These source changes are local. No Asterisk endpoint/dialplan configuration is applied, no live browser/mobile/gateway call has been verified, and event recovery, media/TURN design, service operation, and production rollout remain open. [ARI overview](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/) [ARI setup](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/Getting-Started-with-ARI/).

The user Call Center item appears only when the tenant's active plan and assigned navigation grant the new `telephony.call-center` capability. It exposes only the last tested peer state and channel policy counts assigned to that tenant, not gateway network details or another tenant's channel allocation. Platform Admin can assign each physical channel to an eligible business and associate its unique inbound DID and queue. Changing an enabled channel's tenant/DID/queue requires disabling it in a prior save; inbound eligibility requires an E.164 DID and an enabled queue from the same tenant. These are SaleMaX policy records; Asterisk and Dinstar remain separately provisioned. Owner/manager extension-to-membership mappings have audited, revision-checked APIs and English/Arabic controls. Tenant queue records currently support ring-all across assigned members' mobile/browser endpoints and ring timeout; round-robin and linear strategies are withheld until the ARI controller implements them. Queue records are consumed by the SaleMaX ARI call controller and do not create native Asterisk queues. The local worker starts inside the existing SaleMaX app only when `SALEMAX_ARI_EVENTS_ENABLED=true` and `LOCAL_ONLY_MODE` is not true; it remains off by default. Dialplan, endpoint and network configuration are reviewed previews/manual host work and are not deployed.

## Integration boundaries

- **Platform setup:** encrypted server-side Asterisk control credentials, endpoint reachability, version/compatibility, health, and provisioning/reload status. Never return secrets after save; redact credentials from logs, audit, errors, exports, and UI.
- **Gateway provisioning:** represent each GSM port/channel separately, with enabled state, inbound destination, outbound eligibility, and health. Four slots are a physical channel ceiling, not four concurrent calls per tenant or a promise that the gateway supports a particular control API.
- **Tenant setup:** tenant-owned queues and extension memberships, role permissions, business hours, inbound destinations, and outbound policy. Enforce tenant and member scope on every API operation.
- **Call Center:** authenticated mobile SIP and browser WebRTC endpoints, click-to-call, inbound queue ringing/first-answer-wins, call status, and call controls. Local source now includes endpoint credential lifecycle, signaling client and API-side live call orchestration; the actual Asterisk profile is only a reviewed preview. Agent availability controls, decline/disposition/activity linked to existing leads, production rate limiting, live signaling/media, and real-device call behavior remain open.
- **Events:** run one coordinated, reconnecting server-side ARI WebSocket consumer for the shared PBX; accept the TLS certificate, send ARI authorization in the WebSocket handshake (never in a logged query string), and do not let multiple SaleMaX replicas compete for or duplicate the same PBX event stream. The source worker uses a database singleton lock and bounded reconnect backoff; it handles duplicate call/channel events idempotently. Terminal-state reconciliation after a prolonged disconnect remains open, so live calling must not be treated as production-ready until recovery behavior is implemented and verified. Recordings remain disabled until retention, access, consent, storage, and legal policy are explicitly configured.
- **Network:** the selected topology connects the gateway directly over the internet. Restrict gateway TLS SIP and its bounded RTP media range to the gateway's fixed public source IP, use SRTP, and keep AMI/ARI management endpoints private or restricted to SaleMaX server addresses. Define and verify the required firewall rules before enabling the trunk. Browser calling requires a separately verified WSS, ICE/STUN/TURN, codec, and WebRTC media path; it is not implied by click-to-call.

## Endpoint credential lifecycle and verification

Mobile and browser SIP credentials are derived from the protected SaleMaX platform key with tenant/member/endpoint separation. The platform endpoint preview contains the matching PJSIP auth config and is audited as sensitive access. The owner/manager extension screen can rotate mobile or browser credentials independently; migration `20261112_asterisk_endpoint_credentials.sql` stores a monotonically increasing revision, rejects stale updates, and audits only endpoint type/revision. A reset takes effect for clients after the corresponding Asterisk auth configuration is refreshed from the privileged preview. Never place preview output in logs or tickets.
