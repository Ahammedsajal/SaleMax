# SaleMaX Asterisk and GSM Gateway Integration

Status: local integration slice implemented; no Asterisk or gateway settings have been changed. A read-only production check on 5 October 2026 confirmed the current SaleMaX release does not contain these telephony assets; nothing from this integration is deployed.

## Product scope

Integrate telephony into the existing SaleMaX application. The existing `/admin` platform area owns the global PBX connection, provisioning policy, gateway/route health, and audited setup access. The existing business admin area owns tenant call queues, extension-to-member assignment, schedules, and permitted inbound/outbound policies. Business users receive a **Call Center** item in the existing `/user` sidebar, controlled by the same category, plan, membership, and assigned-navigation checks as other modules. Keep `/admin`, `/admin/login`, `/user`, `/user/login`, and agent entry points intact; do not add another login or application shell.

The selected device is the **four-channel/four-SIM Dinstar UC2000-VE**. Its official datasheet describes both 4- and 8-channel variants, SIP v2/RFC 3261, UDP/TCP/TLS signaling, RTP/SRTP media, optional OpenVPN, VoLTE options, and multiple regional LTE band variants. It lists G.729AB, PCMU, PCMA and G.723.1 codecs; use PCMA/PCMU as the initial Dinstar trunk codec pair and handle browser Opus negotiation separately in Asterisk. The exact regional SKU, firmware, and bands must match the carrier SIMs before purchase or activation. Dinstar's manual describes configuring an IP trunk with the remote SIP server address and port. The intended voice path is four Dinstar channels over a direct-internet, source-restricted PJSIP trunk using TLS signaling and SRTP media, with Asterisk handling extensions, inbound destinations, outbound policy and queues. Configure SIM/channel routing on the Dinstar web UI unless Dinstar confirms a supported voice provisioning API; the listed HTTP API is for SMS. [Dinstar UC2000-VE specifications](https://www.dinstar.com/GSM-3G-LTE-voip-gateway/4-8-ports/) [Dinstar datasheet](https://www.dinstar.com/WEB/files/15277/2018-09-06/UC2000-VE%20GSM%26LTE%20VoIP%20Gateway%20Datasheet.pdf) [Dinstar UC2000-VE/VF/VG user manual](https://www.dinstar.com/WEB/files/15278/2018-09-06/UC2000-VE%26VF%26VG_GSM%20_LTE_VoIP_Gateway_User_Manual.pdf).

Asterisk owns SIP authentication, dialplan, queueing, call recording policy, and provider integration. SaleMaX stores the global ARI endpoint/username and encrypted password from the existing platform-admin panel, and can test both the Asterisk ARI `asterisk/info` response and configured `PJSIP/salemax_dinstar_uc2000ve` endpoint state server-side. The ARI account needs permission to read endpoint status as well as system info. Super Admin setup records the Dinstar fixed public source IP and TLS port, manages inbound/outbound policy for each physical channel, and can apply the three gateway PJSIP peer objects through ARI dynamic configuration. It audits requested, successful, and failed apply attempts without writing credentials to audit. Authenticated mobile and browser profile requests now upsert only the calling member's PJSIP auth/AOR/endpoint through ARI and track extension, password and PBX revisions so unchanged requests do not rewrite live endpoints. Static TLS/WSS transports and the Stasis dialplan still require host configuration. Outbound selectors `9901`–`9904` map to physical `Port-0`–`Port-3`, with four selector digits stripped by the Dinstar route. The SaleMaX API selects the tenant-authorized SIM before originating a call. Each assigned extension now has separate mobile and browser SIP passwords derived from the platform key with tenant/member/endpoint separation. The privileged Asterisk preview contains those passwords and is audited; the authenticated `/api/user/call-center/sip-config` and `/webrtc-config` POST APIs synchronize only the caller's own endpoint profile before returning its credential, and audit access without storing secrets. The Call Center uses TLS/SRTP mobile details and a local SIP.js 0.21.2 bundle for browser WSS/WebRTC registration and audio; setup requires `SALEMAX_ASTERISK_MOBILE_SIP_HOST`, `SALEMAX_ASTERISK_WS_URL`, and the explicit host allowlist. Applying the gateway peer requires Asterisk `res_sorcery_astdb` dynamic mappings for PJSIP endpoint/auth/AOR/identify objects and an ARI account allowed to write configuration; PJSIP transport objects remain static. Asterisk WebRTC still requires its HTTPS/WSS listener or Nginx proxy path, trusted certificate and ICE/media reachability. No browser or mobile credential is an ARI credential. [Asterisk ARI Push Configuration](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/The-Asterisk-Resource/ARI-Push-Configuration/) documents the required dynamic PJSIP provider behavior. [Asterisk WebRTC setup](https://docs.asterisk.org/Configuration/WebRTC/Configuring-Asterisk-for-WebRTC-Clients/). The Asterisk and gateway configs must be applied and tested before calling is reported ready.

**A live ARI HTTP check is not call-control readiness.** The opt-in event worker feeds tenant-bound inbound and outbound call control locally. The inbound dialplan preview now installs one generic `_+X.`/`_X.` route and passes only `${EXTEN}`; SaleMaX normalizes it and resolves the exact enabled DID, channel, tenant, and queue from current policy inside the reservation transaction. Unknown or disabled DIDs fail closed. This means later DID/queue edits do not require per-tenant Asterisk dialplan rewrites, though the generic route itself remains a one-time reviewed host configuration. Inbound calls reserve a unique SIM lease, answer the gateway leg, ring active queue members on mobile and browser endpoints, and apply first-answer-wins. Outbound requests verify the caller's active extension, tenant entitlement, PBX/gateway state, and an enabled tenant-assigned free SIM; the requested endpoint rings first and the Dinstar cellular leg starts after the agent answers. The called number travels through the authorized ARI event and is not persisted. Ended calls release their SIM lease. `GET /api/user/call-center/calls` provides tenant- or membership-scoped call state without phone numbers or raw Asterisk channel IDs. The bilingual Call Center includes a mobile SIP settings reveal, browser SIP.js registration/audio controls, and an outbound call form; browser calls can be selected only after browser SIP registration. These source changes are local. The new Super Admin action applies the Dinstar peer only when the host is already configured for ARI dynamic PJSIP writes; it does not create listeners, transports, dialplan, firewall rules, or gateway routes. No live browser/mobile/gateway call has been verified, and event recovery, media/TURN design, service operation, and production rollout remain open. [ARI overview](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/) [ARI setup](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/Getting-Started-with-ARI/).

The user Call Center item appears only when the tenant's active plan and assigned navigation grant the new `telephony.call-center` capability. It exposes only the last tested peer state and channel policy counts assigned to that tenant, not gateway network details or another tenant's channel allocation. Platform Admin can assign each physical channel to an eligible business and associate its unique inbound DID and queue. Changing an enabled channel's tenant/DID/queue requires disabling it in a prior save; inbound eligibility requires an E.164 DID and an enabled queue from the same tenant. These are SaleMaX policy records; Asterisk and Dinstar remain separately provisioned. Owner/manager extension-to-membership mappings have audited, revision-checked APIs and English/Arabic controls. Tenant queue records currently support ring-all across assigned members' mobile/browser endpoints and ring timeout; round-robin and linear strategies are withheld until the ARI controller implements them. Queue records are consumed by the SaleMaX ARI call controller and do not create native Asterisk queues. The local worker starts inside the existing SaleMaX app only when `SALEMAX_ARI_EVENTS_ENABLED=true` and `LOCAL_ONLY_MODE` is not true; it remains off by default. The gateway peer can be applied through the existing Super Admin setup after a successful ARI check; that write depends on the host dynamic PJSIP backend. Transports, dialplan and network configuration remain manual host work; member SIP profiles are synchronized on authenticated profile requests when the dynamic PJSIP backend is ready.

## Integration boundaries

- **Platform setup:** encrypted server-side Asterisk control credentials, endpoint reachability, version/compatibility, health, and provisioning/reload status. Never return secrets after save; redact credentials from logs, audit, errors, exports, and UI.
- **Gateway provisioning:** represent each GSM port/channel separately, with enabled state, inbound destination, outbound eligibility, and health. Four slots are a physical channel ceiling, not four concurrent calls per tenant or a promise that the gateway supports a particular control API.
- **Tenant setup:** tenant-owned queues and extension memberships, role permissions, business hours, inbound destinations, and outbound policy. Enforce tenant and member scope on every API operation.
- **Call Center:** authenticated mobile SIP and browser WebRTC endpoints, click-to-call, inbound queue ringing/first-answer-wins, call status, and call controls. Local source now includes endpoint credential lifecycle, signaling client and API-side live call orchestration; the actual Asterisk profile is only a reviewed preview. Agent availability controls, decline/disposition/activity linked to existing leads, production rate limiting, live signaling/media, and real-device call behavior remain open.
- **Events:** run one coordinated, reconnecting server-side ARI WebSocket consumer for the shared PBX; accept the TLS certificate, send ARI authorization in the WebSocket handshake (never in a logged query string), and do not let multiple SaleMaX replicas compete for or duplicate the same PBX event stream. The source worker uses a database singleton lock and bounded reconnect backoff, handles duplicate call/channel events idempotently, and on reconnect compares a bounded ARI live-channel snapshot to active SaleMaX legs. It reconciles calls older than 30 seconds to avoid racing new originate requests and releases orphaned channel leases. This recovery path has synthetic database coverage but still needs validation against the deployed Asterisk version and real disconnect/reconnect behavior. Recordings remain disabled until retention, access, consent, storage, and legal policy are explicitly configured.
- **Network:** the selected topology connects the gateway directly over the internet. Restrict gateway TLS SIP and its bounded RTP media range to the gateway's fixed public source IP, use SRTP, and keep AMI/ARI management endpoints private or restricted to SaleMaX server addresses. Define and verify the required firewall rules before enabling the trunk. Browser calling requires a separately verified WSS, ICE/STUN/TURN, codec, and WebRTC media path; it is not implied by click-to-call.

## Private ARI path for the existing container deployment

The production SaleMaX app runs in Docker while Asterisk is installed on the host. The existing app container therefore cannot use `127.0.0.1` to reach host Asterisk, and ARI must not be made publicly reachable. The tracked deployment configuration now defines a dedicated `ari_proxy` bridge (`172.30.240.0/28`) with the app pinned to `172.30.240.2`; `crm.salemax.qa` resolves to Docker's host gateway only inside that app container. The tracked HTTPS Nginx server proxies `/ari/*` to host-loopback `http://127.0.0.1:8088/ari/*` only for that app IP, then returns 403 to other clients. Asterisk HTTP/ARI must bind only to host loopback. Configure the SaleMaX Super Admin ARI URL as `https://crm.salemax.qa/ari`; TLS is verified against the existing public certificate, while both HTTPS and ARI Basic authentication remain in place. The ARI event WebSocket also traverses the restricted `/ari/events` path. Browser SIP uses the separate public `wss://crm.salemax.qa/ws` path: tracked Nginx terminates the existing HTTPS certificate and forwards the WebSocket upgrade to the host-local Asterisk HTTP server, not to the SaleMaX app. PJSIP still authenticates browser registration, while media uses DTLS-SRTP over the configured RTP/ICE path. This route is source-prepared only and must be installed and verified before browser calling. The Nginx template also retains the live-only `/api/user/training/courses/` upload route and its 1025 MB request limit discovered in the active configuration; compare against the live file again before any replacement so existing media uploads stay working.

The Asterisk transport preview now defines one TLS listener, `transport-salemax-tls`, shared by the Dinstar peer and mobile SIP clients. PJSIP does not support separate TLS transports for the same address family; a duplicate gateway/mobile listener would prevent the intended endpoints from coexisting. Because the shared listener must accept both the fixed gateway and remote agent apps, a firewall rule restricted only to the gateway IP would break mobile softphones. Before enabling it, choose either a VPN/SBC path for mobile SIP or public TLS SIP with strong per-device credentials, source-aware rate limiting and intrusion blocking; never expose the unauthenticated ARI interface or broad RTP range. Browser WSS remains on HTTPS 443, separately from this SIP TLS listener.

The selected `172.30.240.0/28` range did not overlap the production host routes or Docker networks during a read-only inspection on 5 October 2026. Recheck the active host routes and Docker IPAM before creating the network on another environment. Applying this tracked Compose change recreates only the app container/network; deploy only after reviewing the active release and rollback path. Install the `/ari/` and `/ws` Nginx locations, then run `nginx -t` before enabling ARI or browser SIP. No production Compose, Nginx or Asterisk file has been changed yet.

Before the first ARI dynamic write, merge these object mappings into `/etc/asterisk/sorcery.conf` while preserving any unrelated existing mappings and then restart Asterisk during the approved maintenance step:

```ini
[res_pjsip]
endpoint=astdb,ps_endpoints
auth=astdb,ps_auths
aor=astdb,ps_aors

[res_pjsip_endpoint_identifier_ip]
identify=astdb,ps_endpoint_id_ips
```

The `res_sorcery_astdb` module must be installed and loaded. Protect Asterisk's AstDB file and backups as secret-bearing runtime data: pushed auth objects include SIP passwords. Keep Asterisk HTTP/ARI bound to `127.0.0.1:8088`; do not publish port 8088 or enable public ARI access. Verify each mapping with the matching `asterisk -rx 'module show like res_sorcery_astdb'` and `pjsip show endpoints` checks after startup before enabling SaleMaX's ARI connection.

The existing Super Admin Asterisk overlay now provides a permission-gated **Preview Asterisk host setup** action with loopback `http.conf`, an `ari.conf` account template containing username/password placeholders, the shared TLS and WSS transport declarations, Sorcery mappings, and the generic DID Stasis contexts. The preview contains no saved ARI or SIP passwords, writes no host files, and does not restart Asterisk. It is an operator-reviewed configuration aid; replace the ARI placeholders with the same values entered in SaleMaX, merge the sections into backed-up host files, and preserve unrelated config. The gateway peer, tenant DID routing, and password-bearing agent endpoints remain separate previews with their own access controls and warnings.
