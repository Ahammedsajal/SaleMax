# 7Network Connected Stores in Retail & Inventory

Updated 6 November 2026. This extends the existing private `retail_boutique@1` category and business panel. The read-only Connected Stores connector is deployed behind closed entitlement/provider gates. Optional WooCommerce product publishing is implemented in source only; migration 33 is not deployed, its worker environment gate is off, and no merchant has authorized writes. See `DEPLOYMENT.md` for the current live release and rollback evidence.

## Product outcome

Give a retail business one owner-only view of orders, payment/refund evidence, customers, products and abandoned checkouts from Shopify and WooCommerce. The connected-store view sits inside the existing Retail & Inventory area and uses the existing business session, tenant boundary, owner permission, language, theme and application shell.

Imported store data remains a separate source ledger. It does not create 7Network storefront orders, reserve stock, send customer messages, reconcile cash, create accounting journals, initiate payments or issue refunds. WooCommerce product publishing is a separate opt-in workflow: an owner maps a 7Network inventory product to a WooCommerce simple product and selects each field to publish. Mapping is always manual; Shopify remains read-only. The publishing feature has not been deployed or enabled.

## Provider coverage

The first release permits one connection per provider store domain across the platform. A provider shop cannot be attached to two 7Network tenants; this keeps webhook routing and privacy compliance requests unambiguous. Product image previews use the source store's HTTPS image URL in the authenticated panel; 7Network does not mirror merchant images in this increment.

| Data/workflow | Shopify | WooCommerce |
|---|---|---|
| Products/customers/orders | GraphQL Admin API with read-only scopes and paginated manual import | REST API v3 with a dedicated read-only consumer key over HTTPS and paginated manual import. Optional outbound product fields use a separate encrypted read/write key and remain off by default. |
| Updates after import | HMAC-signed order, payment, refund, customer, product and app webhooks | HMAC-signed order, customer and product webhooks |
| Payment/refund data | Order transaction/refund records are imported as provider evidence | Order transaction ID and refund records are imported as provider evidence |
| Abandoned checkout | `abandonedCheckouts` query; requires `read_orders` and the authorizing Shopify user’s abandoned-checkout permission | Optional 7Network WordPress connector captures checkout events after the buyer reaches the classic checkout; customer contact is sent only after explicit follow-up consent |
| Privacy lifecycle | Configure the three required compliance webhook topics in the Shopify Dev Dashboard; customer export package and redaction handling are owner reviewed | Owner can disconnect, then erase imported records after typing the exact store domain |

Shopify’s `read_orders` scope covers the last 60 days by default. The optional `read_all_orders` scope must remain disabled until Shopify approves the app, then be enabled in `SALEMAX_SHOPIFY_READ_ALL_ORDERS` and reauthorized. Protected customer data is reviewed separately from scopes. Abandoned checkout visibility also depends on the authorizing staff account’s permission. See the official [Shopify access scope reference](https://shopify.dev/docs/api/usage/access-scopes) and [AbandonedCheckout reference](https://shopify.dev/docs/api/admin-graphql/latest/objects/AbandonedCheckout).

## WooCommerce product publishing and field authority

- **Off by default per store.** A WooCommerce owner must save a separate read/write REST key, map each product, choose fields, and explicitly enable publishing for that store. The existing import key remains read-only. Saving a write key checks read access; WooCommerce has no safe non-writing API permission check, so write access is only confirmed after an approved product update succeeds.
- **Initial supported fields:** 7Network English product name → WooCommerce `name`; product code → `sku`; English description → `description`; current QAR offer → WooCommerce `regular_price`; and available quantity at one selected active 7Network location → `stock_quantity`. Available quantity is on-hand less 7Network reservations. WooCommerce must have stock management enabled for stock publishing.
- **Simple products only.** Variable products and variations, images/media, sale prices, categories, taxes and provider-side product creation are not included. WooCommerce sale price remains owned by WooCommerce. Shopify stays read-only.
- **Field authority rule:** a selected field is eligible for 7Network publishing; an unselected field stays WooCommerce-controlled. Each mapping records a last-accepted value baseline. If WooCommerce still matches that baseline, 7Network may publish a queued local change. If WooCommerce already matches the desired value, the systems are aligned. If it differs from both, the field pauses and the owner must choose.
- **Conflict choice:** “Keep WooCommerce” turns off publishing for that field. “Publish 7Network” shows the current Woo and 7Network values, asks the owner for explicit overwrite confirmation, and records the identity, values and timestamp in the audit ledger. The queued job fetches WooCommerce again. Approval is valid for 24 hours and only while WooCommerce still contains the exact value shown at the worker recheck; a changed value or expired approval opens a new conflict and requires a new owner decision. No last-write-wins behavior is allowed.
- **Provider concurrency limit:** WooCommerce documents product updates through `PUT`, but its standard REST API documentation does not define an atomic conditional update token for that operation ([official product update reference](https://woocommerce.github.io/woocommerce-rest-api-docs/#update-a-product)). The worker checks immediately before writing, which detects changes before that check, but a concurrent WooCommerce edit in the short GET/PUT window cannot be ruled out. Keep the product-publishing environment gate off until a WooCommerce-side atomic compare-and-set extension or an accepted pilot risk is reviewed.
- **Reliability:** product/offer and stock mutations enqueue coalesced durable per-field jobs in their existing transaction. The worker leases jobs, checks current provider state immediately before writing, verifies the returned value, retries transient errors with a bounded attempt count, and surfaces conflicts, retries and permanent errors in Connected Stores. Disconnect clears the write key and pauses publishing. The worker is separately gated by `SALEMAX_RETAIL_WOO_PRODUCT_SYNC_ENABLED=true`.
- **Catalog search:** selectors show the first 500 local and imported products, and owner-only search APIs page through matching 7Network and live WooCommerce products in batches of 50. Search requires two characters and shows product type; the server still validates the selected WooCommerce product immediately before linking. Search availability depends on the existing read-only WooCommerce key.
- **Deployment gates:** confirm the additive migration is backed up and reversible, worker environment remains off until pilot approval, provider write scopes are narrowly assigned, and owner role/two-tenant/EN-AR/PWA and concurrency acceptance passes.

## Data and security design

- Each provider connection is tenant-scoped. Provider credentials, customer/order/checkout snapshots, recovery URLs and raw event payloads use AES-256-GCM with tenant, connection and record identity in the authenticated additional data.
- OAuth state is random, hashed at rest, one-use, short-lived, tenant-bound and actor-bound. Shopify webhooks and Woo webhooks are verified against the exact raw request body before processing.
- Provider requests use HTTPS, bounded response sizes and timeouts, reject redirects, and pin DNS to public IPv4 addresses to limit SSRF and DNS-rebinding risk.
- Webhooks are idempotent by provider delivery ID. Successful and failed-event raw payloads are erased; failed events retain only delivery metadata while the provider retries.
- Customer and payment fields returned to the browser are owner-only. Provider marketing consent, the explicit Woo follow-up consent and 7Network outbound notification consent are distinct values; a provider email-marketing preference never authorizes a 7Network message.
- Product/order/payment imports never write to the 7Network inventory ledger or accounting ledger. The separately gated WooCommerce publisher is the only source-to-source product write; payment state remains labeled as reported by the connected store, not independently settled by 7Network.
- Disconnect revokes credentials and retains imported records for owner reference. After disconnect, the owner can permanently erase imported orders, payment/refund evidence, customers, products, checkouts, privacy requests and event logs; the connection metadata and audit record remain.
- Shopify uses conservative nested connection page sizes to stay within GraphQL query-cost limits. The owner view flags orders, products or checkouts whose nested line items, payment transactions or variants exceed that first page. Full nested pagination or bulk import remains a production gate for stores with large records; it never reports a truncated record as complete.

## Local implementation shape

- Owner screen: `Connected Stores` in the existing business panel, under the current Retail & Inventory capability.
- Shared API: `/api/workspace/retail/connectors` using the current business session/context adapter.
- Provider callbacks: `/api/retail-connectors` for signed provider events and Shopify OAuth.
- Additive schema: `20270132_retail_connected_stores.sql`; optional WooCommerce product publishing adds source-only migration `20270133_retail_woocommerce_product_sync.sql`.
- Woo checkout connector: `integrations/woocommerce/7network-retail-connector.zip` packages `integrations/woocommerce/7network-retail-connector/7network-connector.php` and its install notes. The optional plugin supports classic checkout hooks; WooCommerce Checkout Blocks are not supported by this first version and require a separate extension implementation. Regenerate the archive after changing plugin files.
- Configuration: blank `SALEMAX_SHOPIFY_CLIENT_ID` and `SALEMAX_SHOPIFY_CLIENT_SECRET`; pinned GraphQL version `2026-10`; optional historical orders scope disabled by default.

## Rollout plan

1. **Source readiness:** finish provider schema and query review, current API/payload review, permission boundaries, tenant isolation, duplicate delivery and failure recovery behavior. Run meaningful disposable-database and concurrency checks before declaring the source increment complete.
2. **Provider readiness:** configure the Shopify app callback at `https://7network.live/api/retail-connectors/shopify/callback`, add the client credentials to the protected production environment, receive required scope/protected-customer-data approvals, configure the mandatory static privacy webhook endpoint, and set the approved API version. For WooCommerce, produce a read-only REST key and configure each signed webhook; the merchant installs the optional plugin only if they want abandoned checkout capture. Product publishing additionally needs the verified source/migration, the worker environment gate, an owner-supplied dedicated read/write key and an approved pilot.
3. **Staging:** production migration 32 is applied through the existing migration ledger, and its nine connector tables are empty. Before connecting a merchant, verify fresh/upgrade migration behavior in staging, connect synthetic Shopify and Woo stores, and exercise pagination, webhook retries, duplicate deliveries, customer data requests/redaction, disconnect and owner erase.
4. **Acceptance:** sign in as a pilot owner; verify staff/agent denial, two-tenant isolation, imported orders/payments/customers/products/checkouts, manual sync and webhook updates, explicit checkout consent, Arabic/RTL, English, light/dark, keyboard/screen reader states, mobile/tablet/desktop, installed PWA and offline/update behavior.
5. **Operations:** complete custom-domain TLS where applicable, provider rate-limit monitoring, alerting and runbooks, load/restore rehearsal, privacy/export retention policy and pilot approval. Deploy the verified source, record migration, release, rollback and health evidence in `DEPLOYMENT.md`, then roll out to selected merchants. Keep public storefront activation and online payment/refund/accounting posting separately gated.

## Current gates

The read-only connector source and migration 32 are deployed; no Shopify app credentials or protected-data approvals are configured, no Woo merchant key/plugin pilot is connected, and no signed-in owner/staff or two-tenant acceptance has been completed. The separate WooCommerce product-publishing implementation and migration 33 are source-only, not deployed; its worker environment gate remains off, no write key is saved and no provider product update has been made. The page remains inaccessible to business tenants until a reviewed commerce plan is assigned. The privacy export package deliberately fails instead of silently truncating when a customer has more than 5,000 imported orders or checkouts; larger exports need an asynchronous, paginated export job before production acceptance. The optional Woo plugin does not support Checkout Blocks. The deployed connector performs no inventory update, payment capture/refund, accounting posting or customer outreach. Searchable product selectors return up to 50 matches per page; owner-facing signed-in acceptance is still required.

Do not mark this integration or the wider retail rollout complete until these gates and the existing retail plan’s open finance, PWA, accessibility, custom-domain TLS and load/restore work are verified.
