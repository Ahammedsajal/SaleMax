This audit records preconditions for adding application instances; it does not approve a scale-out or change production.

## Verified live state

- The 22 October pre-overlay inspection found host `carsqatar-prod-01` running one SaleMaX app container, MariaDB, a report worker and a recruitment notification worker. At that snapshot the release was `/opt/salemax/releases/7network-domain-activation-485c2d0-20261022`, app image `sha256:66b58843131e2b5112d81a363a679bfa729c86ba105e9207adb8fbb3266df8c1`, root disk 85% used with 7.2 GiB available, and inode use 21%; app and worker image identities differed. The snapshot's `SOURCE_COMMIT` marker (`cf60781`) differed from that time's ledger source (`485c2d01`). The later Inbox follow-up release `/opt/salemax/releases/inbox-follow-up-8e0a62b-20261022` replaced only the app container and retained the other services. Current disk/inode usage, current marker alignment, and current app/worker image identity alignment were not remeasured in that deployment record.
- Root, `/opt/salemax/shared/media` and `/opt/salemax/shared/sessions` are on the host's `/dev/sda1` ext4 filesystem. Compose bind-mounts media, Meta media, course media, tenant logos, recruitment CVs, channel sessions, themes and license files from `/opt/salemax/shared`. These mounts persist across a container replacement on this host; they are not shared storage across hosts.
- A metadata-only privileged inventory found 54 files / 84.1 MB in media, 403 / 154.5 MB in Meta media, 18 / 1.37 MB in course media, 8,243 / 3.13 MB in QR sessions, and 17 / 0.15 MB in themes. Tenant-logo and recruitment-CV roots were empty at this check. No filenames or file contents were read. These aggregates are a point-in-time migration inventory, not a growth estimate.
- Training payment-proof storage is disabled in the active app environment: `SALEMAX_PAYMENT_PROOF_ROOT` is unset. Configure and verify durable private proof storage before enabling that upload workflow; its path cannot be treated as covered by the current Compose mounts.
- The live `web_private.qr_storage` value is `local`. The active app reports two QR connections. Baileys credentials use `/app/sessions` when local mode is active; the path is backed by the host-only sessions bind mount. Baileys MySQL and MongoDB adapters exist in source, but neither is currently selected in production. The in-memory QR connection maps still need per-channel ownership and handover before a second app can connect to the same WhatsApp account.
- Canonical web authentication stores only a token hash in the InnoDB `sx_sessions` table and resolves membership from MariaDB on requests. That is a useful shared session foundation when all instances use the same database. Socket.IO is initialized with the default in-process adapter; no shared pub/sub adapter is configured, so live events and connection-state recovery are not shared across app instances.
- Legacy chat JSON is read as a fallback beside database messages. `/app/conversations/inbox` is absent in the active container, so no legacy JSON files were found there during this check. Do not copy or mount an empty directory as though it were the authoritative conversation store; verify future writes and retain the database record path.
- The app starts the CRM account sync worker, receipt and task notification workers, Asterisk event worker, campaign scheduler, QR warmer and WhatsApp retention scheduler from its server process. `initCampaign()` runs in each app process and guards campaign IDs with a local JavaScript `Set`; it selects `PENDING` and `IN_PROGRESS` campaigns without a database claim. The CRM account sync worker also selects pending rows without a cross-process claim and relies on process-local flags/sets. The QR warmer recursively schedules another pass. These source paths have no demonstrated cross-instance ownership guarantee.
- Campaign recipient delivery has an additional crash window: a log remains `PENDING` while the external Meta send is in flight, then becomes `SENT` only after a message ID returns. Two app processes can select the same log, and a process crash after Meta accepts the send but before the database update leaves it eligible to send again. A lease alone cannot resolve that ambiguous external outcome. Before enabling multi-instance campaign workers, introduce an atomic recipient claim and explicit `sending`/`unknown` outcome handling, confirm whether the provider supports a usable idempotency key, and require operator-safe reconciliation for ambiguous outcomes. Do not blindly reclaim and resend a log whose provider result is unknown.
- Some independent workers already use database coordination: task notifications, report deliveries and recruitment founder notifications claim rows with transactional `FOR UPDATE SKIP LOCKED` and expiring leases. The Asterisk event worker holds a MariaDB advisory lock. These are useful patterns, but they do not cover the campaign, CRM account sync, QR connection, or every scheduled maintenance path.
- The host has an active Oracle unified monitoring agent and `sysstat` collection. Seven-day host averages show CPU idle at 94.89–96.26% on complete days and 9.36–9.55 GiB of average available memory; these include Carsqatar and are not peak, tenant concurrency, or app-only measurements. The initial disk snapshot was 85% used with 7.8 GB free; the later same-day recheck is recorded above. No host disk-alert timer was found; OCI cloud alarms and notification topics were outside the available read-only SSH view.

## Source-level upload and mounted-data audit

The following is a repository code-path inventory, not a claim that every flow is active in production. The deployment-time host counts above remain the only live file inventory; database-backed paths, hashes and per-tenant manifests have not yet been reconciled against the mounted files.

- Public legacy media is written by existing user/admin/agent and Meta routes into `client/public/media` or `client/public/meta-media`. `/media` and `/meta-media` use Express static serving with long public cache headers and byte-range support. Those directories are mounted from `/opt/salemax/shared`; the bind mounts hide any image-shipped files at those paths. Inventory and preserve the shipped 7Network brand assets and any other required defaults before changing the mount or moving these files. These URLs are public by design and must not become storage for private proofs, CVs, or other restricted files.
- Tenant CRM logos are stored under the configured `SALEMAX_CRM_LOGO_ROOT`, with tenant UUID directories and UUID filenames, and are served from `/api/crm/logos/:tenantId/:filename` after tenant-context checks. Training-center profile logos use a separate `client/public/media/training-center-logos` path and are public static media. Treat the two logo flows as distinct data classes and preserve their existing visibility rules.
- Course/product media is written beneath `SALEMAX_COURSE_MEDIA_DIR` (default `database/local-runtime/course-media`) using tenant/course/media UUID hierarchy, MIME signature checks, SHA-256, per-tenant quota checks, and database rows. Course downloads use short-lived tenant/course/media JWT access, while the QR chatbot reads the same local path immediately before sending. The production Compose mount makes this path host-persistent but not shared across hosts.
- Recruitment CVs use `SALEMAX_RECRUITMENT_CV_ROOT` and tenant/application-scoped keys. The application route is owner-only, returns `private, no-store`, and streams the file after authorization. WhatsApp CV intake first resolves public Meta media and copies validated PDF/DOCX bytes into this private root. The root must remain private and must not be replaced with an unauthenticated object URL.
- Training payment proofs use `SALEMAX_PAYMENT_PROOF_ROOT`, tenant/payment-scoped keys, SHA-256/MIME metadata and finance permission checks; reads return a local path for the authorized router to stream. The live audit found this environment root unset, so proof upload remains disabled and no live proof directory was counted.
- The Compose mount `/opt/salemax/shared/themes:/app/routes/themes` preserves runtime theme JSON and registry state. The app seeds missing defaults from adjacent source JSON into that mounted directory, so an empty mount can hide shipped theme defaults; do not replace or initialize it without a read/backup/manifest reconciliation.

Any durable shared-storage adapter must preserve the tenant/object associations, authorization guards, content-signature validation and limits already enforced by each upload flow. Keep private reads behind the existing authorized routers; retain stable `/media`, `/meta-media`, course-download and tenant-logo URL behavior where required. The source candidate now has a private local/S3-compatible adapter wired into course media (including chatbot, quick-reply and QR/Meta reply paths), payment proofs, and recruitment CV upload/download. Each private namespace can select `local` or `s3` independently using `SALEMAX_COURSE_MEDIA_STORAGE_DRIVER`, `SALEMAX_PAYMENT_PROOFS_STORAGE_DRIVER` and `SALEMAX_RECRUITMENT_CVS_STORAGE_DRIVER`; `SALEMAX_OBJECT_STORAGE_DRIVER` remains a shared fallback and all defaults remain local. `tests/object-storage.test.cjs` covers local safety, an injected S3 client and per-namespace selection; this does not establish compatibility with a selected live provider.

The new `scripts/migrate-private-objects-to-s3.cjs` can write a mode-0600 manifest outside the checkout for `course-media`, `payment-proofs` or `recruitment-cvs`, keyed by tenant UUID and recording byte count/SHA-256 without source paths. Its apply mode copies from an absolute local root, refuses changed sources or conflicting remote objects, re-downloads and hashes each target, and never deletes source files. The CLI requires the shared-lock marker, active release context, an already-existing regular lock file held by a live OS `flock`, and S3 configuration for the namespace being migrated; it checks the held lock without creating the lock file. Input manifests must be regular owner-only files outside the checkout. Once bootstrapped, invoke it inside `/opt/salemax/shared/with-production-lock.sh` so the same lock remains continuously held for the operation. No provider, bucket, credentials or production manifest have been configured, and no production migration or storage-driver switch has been made. Still required: reconcile every DB record with the live mounted files, prove selected provider behavior and private authorized/denied reads, test rollback with retained local source, and schedule a locked cutover only after these checks.

## Required before adding app instances

The source candidate now routes `SIGTERM` through an explicit asynchronous
shutdown coordinator: it closes Socket.IO, stops its known child workers,
cleans up Telegram/QR connections, then re-delivers the signal, with a 25s hard
deadline. Compose enables a small init process and grants the app 30s to stop.
Unit tests cover signal relay, cleanup failure and the hard deadline. This
source-level change is not yet deployed or container-accepted. It does not
cancel every embedded campaign, CRM-sync, QR-warmer or retention timer, nor
does it make external sends safe across crashes. Those ownership and
in-flight-work contracts must be completed before scale-out.

1. **Durable shared files:** inventory every upload/output path, including public media, private proofs, generated documents, recordings, themes and any remaining local conversation files. Move supported files to a durable object store or genuinely shared filesystem. Migrate with checksums and a per-tenant manifest, verify reads and authorization, then retire local writes. A Docker bind mount under `/opt/salemax/shared` is single-host persistence, not a multi-host design.
2. **Channel credentials and ownership:** back up and migrate the live local Baileys auth data to a supported shared store without disconnecting customer channels. Add one active owner lease per channel, lease renewal, stale-owner fencing, and a controlled handoff/reconnect path. Test two workers against synthetic channels and prove that only one sends or receives for a channel at a time.
3. **Websocket fanout:** select and configure a shared Socket.IO adapter. Test authenticated reconnects, tenant-bound rooms, revocation, origin checks and cross-instance event delivery with two app processes. Preserve the current session revalidation; a shared adapter does not replace authorization.
4. **Worker separation and duplicate control:** web replicas must not each start the same scheduler. Move singleton schedulers to named Compose worker roles or guard each job with a database lease. Convert legacy campaign and CRM-sync processing to atomic per-item claims. For external sends, define lease expiry, retry and ambiguous-provider-outcome behavior; a stale `sending` state must not automatically become resendable `PENDING` work unless provider idempotency or reconciliation makes that safe.
5. **Cross-instance acceptance:** with two app instances and synthetic tenants, verify same-category and cross-category isolation for sessions, HTTP APIs, sockets, media grants, search, campaign delivery, channel ownership and worker retries. Exercise process loss during upload and during each external send; confirm rollback and data retention.
6. **Capacity and database plan:** collect app/worker-specific peak CPU, RSS, disk I/O, database connection counts, query latency, queue age and tenant fairness under representative load. Separately design database capacity, backup consistency across DB and media, restore time targets, and a tested recovery drill. Do not infer these from current low host averages.
7. **Operational alerts:** configure an operator-visible disk alert at the documented thresholds, plus image/release growth and database/worker health alerts. Verify delivery with a simulated event before treating monitoring as complete.

Until these checks pass, keep the deployment at one app instance. The current single-host bind mounts and per-process schedulers are explicit migration work, not an implicit guarantee of horizontal scalability.
