## Source-level upload and mounted-data audit

The following is a repository code-path inventory, not a claim that every flow is active in production. The deployment-time host counts above remain the only live file inventory; database-backed paths, hashes and per-tenant manifests have not yet been reconciled against the mounted files.

- Tenant CRM logos are stored under the configured `SALEMAX_CRM_LOGO_ROOT`, with tenant UUID directories and UUID filenames, and are served from `/api/crm/logos/:tenantId/:filename` after tenant-context checks. - Recruitment CVs use `SALEMAX_RECRUITMENT_CV_ROOT` and tenant/application-scoped keys. The application route is owner-only, returns `private, no-store`, and streams the file after authorization. Any durable shared-storage adapter must preserve the tenant/object associations, authorization guards, content-signature validation and limits already enforced by each upload flow. Keep private reads behind the existing authorized routers; retain stable `/media`, `/meta-media`, course-download and tenant-logo URL behavior where required. ## Required before adding app instances

The source candidate now routes `SIGTERM` through an explicit asynchronous
shutdown coordinator: it closes Socket.IO, stops its known child workers,
cleans up Telegram/QR connections, then re-delivers the signal, with a 25s hard
deadline. Compose enables a small init process and grants the app 30s to stop.
Unit tests cover signal relay, cleanup failure and the hard deadline. This
source-level change is not yet deployed or container-accepted. It does not
cancel every embedded campaign, CRM-sync, QR-warmer or retention timer, nor
does it make external sends safe across crashes. Those ownership and
in-flight-work contracts must be completed before scale-out.

1. **Durable shared files:** inventory every upload/output path, including public media, private proofs, generated documents, recordings, themes and any remaining local conversation files. Move supported files to a durable object store or genuinely shared filesystem. Migrate with checksums and a per-tenant manifest, verify reads and authorization, then retire local writes. A Docker bind mount under `/opt/salemax/shared` is single-host persistence, not a multi-host design.
2. **Channel credentials and ownership:** back up and migrate the live local Baileys auth data to a supported shared store without disconnecting customer channels. Add one active owner lease per channel, lease renewal, stale-owner fencing, and a controlled handoff/reconnect path. Test two workers against synthetic channels and prove that only one sends or receives for a channel at a time.
3. **Websocket fanout:** select and configure a shared Socket.IO adapter. Test authenticated reconnects, tenant-bound rooms, revocation, origin checks and cross-instance event delivery with two app processes. Preserve the current session revalidation; a shared adapter does not replace authorization.
4. **Worker separation and duplicate control:** web replicas must not each start the same scheduler. Move singleton schedulers to named Compose worker roles or guard each job with a database lease. Convert legacy campaign and CRM-sync processing to atomic per-item claims. For external sends, define lease expiry, retry and ambiguous-provider-outcome behavior; a stale `sending` state must not automatically become resendable `PENDING` work unless provider idempotency or reconciliation makes that safe.
5. **Cross-instance acceptance:** with two app instances and synthetic tenants, verify same-category and cross-category isolation for sessions, HTTP APIs, sockets, media grants, search, campaign delivery, channel ownership and worker retries. Exercise process loss during upload and during each external send; confirm rollback and data retention.
6. **Capacity and database plan:** collect app/worker-specific peak CPU, RSS, disk I/O, database connection counts, query latency, queue age and tenant fairness under representative load. Separately design database capacity, backup consistency across DB and media, restore time targets, and a tested recovery drill. Do not infer these from current low host averages.
7. **Operational alerts:** configure an operator-visible disk alert at the documented thresholds, plus image/release growth and database/worker health alerts. Verify delivery with a simulated event before treating monitoring as complete.

Until these checks pass, keep the deployment at one app instance. The current single-host bind mounts and per-process schedulers are explicit migration work, not an implicit guarantee of horizontal scalability.
